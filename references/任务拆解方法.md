# 任务拆解方法

## 1. 何时拆解

简单、单步骤、低风险任务可以直接描述执行动作。

出现以下情况时建议拆解：
- 多个不同交付物；
- 多个执行角色或工具；
- 存在前置依赖；
- 修改范围较大；
- 需要阶段审查；
- 失败成本较高；
- 需要并行执行。

## 2. 分解原则

- 按可交付结果拆分，不只按操作动作拆分。
- 每个子任务有明确输入和输出。
- 子任务尽可能独立验收。
- 明确前置依赖，避免隐式顺序。
- 不过度拆分成大量微任务。
- 先盘点和审查，再实施高影响修改。
- 关键阶段设置用户检查点。

## 3. 子任务定义

```markdown
### TASK-01｜任务名称
- 目标：
- 前置条件/依赖：
- 输入：
- 执行动作：
- 输出：
- 验收标准：
- 用户确认点：
```

## 4. 阶段门禁

典型阶段：
1. 资料盘点；
2. 方案/设计；
3. 实施；
4. 自检与验证；
5. 交付与报告。

不是所有任务都需要五阶段。依据风险和复杂度裁剪。

## 5. 依赖表达

- TASK-02 依赖 TASK-01；
- TASK-03 与 TASK-04 可并行；
- TASK-05 必须在用户确认 TASK-02 方案后开始。

不要创建无法解释的复杂依赖图。
