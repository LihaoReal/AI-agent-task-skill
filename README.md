# Task Architect

通用型 AI 任务规划与任务书编制 Skill，默认采用“多轮交互 + 用户审查后定稿”。

## 目录结构

```text
AI-agent-task-skill/
├── SKILL.md
├── README.md
├── references/
│   ├── 需求分析方法.md
│   ├── 任务拆解方法.md
│   ├── 验收标准设计.md
│   └── 任务书质量检查清单.md
└── templates/
    ├── 通用任务书模板.md
    ├── 软件开发任务书模板.md
    ├── 知识库建设任务书模板.md
    └── 工程技术任务书模板.md
```

## 安装到 WorkBuddy

1. 将本仓库克隆或下载到 WorkBuddy 支持的自定义 Skill 目录。
2. 确保 `SKILL.md` 位于 Skill 根目录。
3. 保留 `references/` 和 `templates/` 相对目录。
4. 在 WorkBuddy 中刷新/重新加载 Skill（具体入口以当前版本为准）。
5. 使用下方测试用例验证触发和交互行为。

如果 WorkBuddy 的 Skill 格式有额外要求，先按平台规范适配，不要删除本 Skill 的交互和权限约束。

## 推荐调用方式

- “使用 Task Architect，帮我把这个想法整理成任务书：……”
- “使用 Task Architect，先分析需求并问我关键问题，暂时不要写任务书。”
- “使用 Task Architect，审查下面这份任务书，指出阻断问题。”
- “使用 Task Architect，按精简版输出初稿。”

## 验证用例

### 用例 1：模糊需求
输入：“我想做一个元器件知识库。”
预期：先概括目标，识别首要缺口，提出一个关键问题；不立即输出大篇幅任务书。

### 用例 2：已有输入和边界
输入：“读取指定文件夹的 PDF，按现有模板建立案例，不修改基础规范，不推送 GitHub。”
预期：识别已明确的信息，不重复询问；重点澄清仍影响执行的范围或输出问题。

### 用例 3：代码重构
输入：“帮我优化现有 Python 状态机。”
预期：区分代码审查与代码修改，澄清行为兼容、修改范围、测试和提交权限。

### 用例 4：用户要求直接初稿
输入：“信息不全的地方标待确认，先直接出初稿。”
预期：生成初稿，将假设和待确认项显式标记，不把草稿说成最终批准版本。

## 设计约定

- Skill 负责需求分析和任务书编制，不自动执行任务书。
- 用户确认定稿与用户授权执行是两个独立动作。
- 专业知识应来自用户资料、可信来源或明确标注的假设。
