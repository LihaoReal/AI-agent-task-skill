# Task Architect Skill V1.1 修改清单

## 1. 版本目标

V1.1 的目标不是扩大 Skill 的功能范围，而是针对 V1.0 首轮测试中发现的问题，提升需求对齐效率、任务现状判断能力和执行权限安全性。

**版本原则：小步迭代、规则清晰、可测试、保持 V1.0 已验证能力。**

## 3. 详细修改项

### V11-01：任务意图预判（P0）

**问题来源：** V1.0 测试中，用户的真实目的是验证 Skill 流程，但初始需求容易被直接解释为实际知识库建设任务。

**拟增加规则：**

将任务意图分为三类：

1. **流程验证**：验证 Skill、Agent 或工作流程，不实际执行目标任务。
2. **实际执行**：希望完成具体工作，需要编制可执行任务书；任务书确认和执行授权仍然分离。
3. **方案设计**：只需要研究、分析、设计或规划，不默认进入实施。

**交互要求：**

- 优先从用户表达自动识别，不要求每次固定选择。
- 意图明确时直接进入对应流程。
- 存在歧义时，才提出一个简短澄清问题。
- 流程验证应输出测试目标、场景、预期行为、观察结果和结论。
- 方案设计应明确方案交付边界，不默认开展实际实施。

**验收标准：**

- 输入“测试一下这个 Skill”时，识别为流程验证，不生成真实业务执行任务。
- 输入“帮我开发一个 LDO WCCA Skill”时，识别为实际执行意图，进入需求澄清。
- 输入“帮我设计 WCCA Skill 架构，只讨论方案”时，识别为方案设计，不安排实际文件修改。
- 意图模糊时只提出当前最关键的一个问题。

### V11-02：执行授权分层（P0）

**问题来源：** V1.0 任务书将部分文件修改列为“允许”，容易与用户尚未授权执行的状态混淆。

**拟增加规则：**

任务书必须区分以下三个概念：

| 概念 | 含义 |
|---|---|
| 建议执行范围 | 为完成目标，方案建议执行哪些操作；不代表已获授权 |
| 已批准执行权限 | 用户明确批准后，Agent 当前实际可以执行的操作 |
| 禁止操作 | 未经额外授权不得执行，或本任务明确不允许的操作 |

**强制约束：**

- 任务书初稿阶段，默认只描述建议执行范围，不得把它写成已经生效的执行许可。
- 用户确认任务书，只表示确认任务定义；不自动授权文件修改、代码变更、Git 提交/推送或外部操作。
- 执行前必须检查是否存在明确、具体的执行授权。
- 授权应尽可能限定对象、操作、范围和有效阶段。
- 新增高影响操作或扩大范围时，暂停并重新征求授权。
- 用户明确授权只覆盖其表达的范围，不可推定为无限授权。

**验收标准：**

- 用户只说“任务书确认”时，Agent 不执行文件修改或 Git 操作。
- 用户只授权“读取和分析”时，Agent 不修改文件。
- 用户明确授权修改指定文件时，Agent 不将授权扩展到模板、规范或其他文件。
- 未授权的删除、覆盖、推送等操作均暂停确认。

### V11-03：任务现状调查（P1）

**问题来源：** 本次测试中，WorkBuddy 主动报告已有案例、索引和问题清单，避免机械地从零生成，体现出很高的实际价值。

**拟增加规则：**

当任务涉及已有项目、代码仓库、知识库、设计文件或历史成果时，在任务拆解前增加轻量现状调查：

- 已有输入和成果；
- 当前完成状态；
- 现存问题和未关闭事项；
- 相关规范、模板和约束；
- 可能重复建设或冲突的内容；
- 本次任务与已有成果的关系。

调查结果必须区分：

- 已实际读取并核实；
- 工具或用户报告但尚未独立核实；
- 根据现有信息推断；
- 当前不可访问/未知。

不得把文件名、目录名或工具摘要直接当作已核验的文件内容。

**任务路线识别：**

根据调查结果判断本次工作更接近：
- 新建；
- 继续；
- 复核；
- 补全；
- 修复；
- 迁移；
- 仅验证。

**验收标准：**

- 对已有项目的任务，任务书能列出相关已有成果和待核实项。
- 发现已有成果时，明确说明是复用、更新还是新建。
- 无法访问资料时明确标记未知，不虚构调查结论。
- 对简单、全新且无既有资产的任务，不强制执行冗余盘点。

### V11-04：逐轮澄清约束（P1）

**问题来源：** V1.0 任务书在正文聚焦一个阻断问题，但末尾一次性要求用户确认多个事项。

**拟增加规则：**

- 每轮只提出一个当前最关键的问题。
- 多个问题存在依赖关系时，按先后顺序逐轮提出。
- 不在任务书末尾重新堆叠尚未按顺序澄清的问题。
- 已明确的信息不重复询问。
- 可把其他待确认项记录在内部需求清单中，但当前只向用户提出优先级最高的一项。
- 只有当多个信息必须一起提供且明显更省事时，才合并提问。

**验收标准：**

- 存在任务方向阻断项时，先只询问任务方向。
- 方向确定后，再询问影响方案的下一个关键问题。
- 最终任务书中的待确认事项与对话澄清状态一致，不出现已回答问题仍要求确认的情况。

### V11-05：成熟度判定约束（P1）

**问题来源：** V1.0 任务方向尚未确定时，WorkBuddy 仍给出 M3。

**拟增加规则：**

- 成熟度必须反映需求和方案的实际确定程度，不能因为任务书章节齐全就提高等级。
- 存在影响任务目标或路线的阻断性问题时，原则上不得评为 M3。
- M3 至少要求目标、主要输入、范围、执行步骤、交付物、权限和验收基本明确。
- M4 还要求质量检查完成且用户明确确认定稿。
- 同时列出未解决阻断项及其对成熟度的影响。

**验收标准：**

- A/B/C 执行路线尚未确认时，不得将该任务评为 M3。
- 仅有初步想法时评为 M0/M1，不为追求完整而补造信息。
- 用户确认任务书之前，不得评为 M4。
- 不因非阻断性偏好未确定而过度降低成熟度。

### V11-06：验收标准可验证性（P1）

**问题来源：** V1.0 部分验收项仍使用“内容一致”“链接有效”等概括性表述。

**拟增加规则：**

每项验收标准尽可能包含：

1. 检查对象；
2. 检查范围或覆盖率；
3. 检查方法；
4. 通过条件；
5. 证据或记录；
6. 无法自动判断时的人工评审要求。

对工程、硬件和数据分析任务，应关注来源定位、测试条件、计算边界、假设和人工工程判断。

**验收标准：**

- 不使用只有主观形容词、没有判断方法的验收项。
- 每个关键交付物至少有一项可验证标准。
- 自动检查与人工评审明确区分。
- 不可验证的要求应改写、补充证据要求或标记为待确认。

### V11-07：固定回归测试集（P2）

**目的：** 防止后续规则增加后，原有能力退化或 Skill 过度复杂化。

**建议测试集：**

| 用例 | 场景 | 主要验证点 |
|---|---|---|
| TC-01 | 模糊想法：“我想做一个元器件知识库” | 需求理解、单问题澄清 |
| TC-02 | 已有知识库，要求补充 Datasheet | 现状调查、复用已有成果 |
| TC-03 | “测试一下这个 Skill” | 流程验证意图识别 |
| TC-04 | “只设计方案，不执行” | 方案设计边界 |
| TC-05 | “任务书确认”但未授权修改 | 执行授权分离 |
| TC-06 | 用户只授权读取，不授权写入 | 权限范围控制 |
| TC-07 | Python 状态机优化 | 审查与修改区分、兼容性和测试要求 |
| TC-08 | 用户中途改变任务目标 | 变更识别、重新澄清 |
| TC-09 | 关键资料无法访问 | 未知标记、禁止虚构 |
| TC-10 | 用户要求直接出初稿 | 假设和待确认项显式标注 |

**回归测试判定：**

- PASS：满足该用例全部关键预期。
- PARTIAL：核心方向正确，但存在非阻断偏差。
- FAIL：违反关键需求、权限或安全边界。
- BLOCKED：因测试环境或输入不足无法判断。

## 5. 预计涉及文件

建议 V1.1 修改时优先控制在以下文件：

- `SKILL.md`：新增或调整核心行为规则。
- `references/需求分析方法.md`：补充任务意图预判和现状调查方法。
- `references/任务书质量检查清单.md`：补充权限分层、成熟度和逐轮澄清检查项。
- `references/验收标准设计.md`：补充验收证据和可验证性要求。
- `README.md`：更新版本说明和回归测试入口。
- `tests/回归测试用例.md`：新增固定测试集。

不建议为了 V1.1 同时重写所有模板。只有当核心规则变化确实影响模板字段时，再做最小必要调整。

## 6. V1.1 完成验收标准

V1.1 至少满足以下条件后，才建议标记为完成：

- [ ] 三类任务意图能够正确识别，歧义时再询问。
- [ ] 任务书建议范围与已批准执行权限明确分离。
- [ ] 涉及既有项目时能够开展适度现状调查，并标注证据可信状态。
- [ ] 关键澄清按依赖顺序逐轮提出。
- [ ] 成熟度不会与未解决的阻断问题冲突。
- [ ] 关键验收项具备对象、方法、通过条件和证据。
- [ ] 固定回归测试集已建立并执行。
- [ ] 原有 V1.0 用例没有出现关键能力退化。
- [ ] 更新记录、README 和版本信息一致。

## 7. 本次不纳入 V1.1 的事项

为控制迭代范围，以下内容暂不纳入：

- 自动执行用户任务或自动修改项目文件；
- 自动创建 Git 分支、提交或推送；
- 引入复杂的多 Agent 编排机制；
- 增加繁重的项目管理表单或强制问卷；
- 重构全部任务书模板；
- 引入复杂评分算法或过度细化的成熟度量表。

## 8. 版本决策

- V1.0：保留为首轮测试通过的基线。
- V1.1：按本清单实施最小必要修改，完成后执行回归测试。
- 本清单是修改计划，不代表 V1.1 已实施，也不代表相关行为已经生效。
