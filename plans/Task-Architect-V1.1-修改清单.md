# Task Architect V1.1 修改清单

- **当前基线**：V1.0
- **目标版本**：V1.1
- **规划日期**：2026-11-03
- **状态**：待评审，尚未实施
- **修改原则**：小步迭代，保留 V1.0 基线；优先修正流程和权限语义，不为增加功能而增加复杂度。

## 1. V1.1 目标

在不改变 Task Architect 核心定位的前提下，提升以下能力：

1. 更早识别用户本次任务意图；
2. 将任务现状调查纳入标准流程；
3. 严格执行单问题逐轮澄清；
4. 提高任务成熟度判断的一致性；
5. 明确区分任务书建议权限与实际执行授权；
6. 让验收标准更容易检查和判定。

V1.1 仍然只负责需求分析、方案设计和任务书编制，不因版本升级而自动获得执行任务的权限。

## 3. 具体修改要求

### V11-01：任务意图三态预判（P0）

**修改位置建议**：`SKILL.md` 的“默认工作模式”及“六阶段工作流程”中的需求接收阶段。

增加三类意图：

- **流程验证**：验证 Skill、Agent 或工作流程，不开展目标任务本身。
- **实际执行**：用户希望最终完成具体工作，需要编制任务书并等待授权。
- **方案设计**：只需要分析、研究、设计或规划，不默认安排实际实施。

行为规则：

1. 优先根据用户自然语言自动判断，不机械要求用户每次选择。
2. 意图明确时直接进入相应流程。
3. 存在歧义且会影响交付物或工作范围时，询问一个最关键的问题。
4. 流程验证任务以测试目标、测试场景、预期行为、观察结果和改进建议为主要交付。
5. 方案设计任务以方案、取舍、风险和建议为主要交付，不默认产生执行授权。
6. 实际执行意图仍须经过任务书审查、定稿和独立执行授权。

**验收标准**：

- 输入“测试一下这个 Skill”，应识别为流程验证，不应直接生成真实项目执行任务书。
- 输入“设计一个 WCCA Skill 架构”，应识别为方案设计。
- 输入“帮我开发并交付一个 WCCA Skill”，应识别为实际执行意图。
- 输入含糊时，应提出一个关键澄清问题。

### V11-02：增加任务现状调查（P0）

**修改位置建议**：在需求分析之后、任务拆解之前增加一个明确步骤；同步更新流程图或阶段说明。

调查内容按任务类型选择，不要求每个任务都进行全面扫描：

- 软件开发：代码仓库、现有模块、接口、测试、未解决问题。
- 硬件工程：设计文件、Datasheet、计算书、设计约束、问题清单。
- 知识库：目录、模板、规范、已有文档、重复内容、缺口。
- Skill/Agent：现有 Skill 文件、触发规则、工具权限、测试用例和历史版本。
- 研究分析：已有资料、已形成结论、证据缺口和时效性。

必须区分：

- 已通过工具或资料核实；
- 用户明确提供；
- Agent 推断；
- 当前不可访问或尚未核实。

调查结论应回答：哪些已有成果可复用、哪些内容尚未完成、是否存在重复建设、是否需要改变原始任务目标。

**验收标准**：

- 对已有成果的任务，能识别可复用资产并说明调查依据。
- 无法访问的路径或文件必须明确标记，不得声称已检查。
- 不因调查发现已有成果就擅自修改或删除它们。
- 简单任务允许跳过调查，并说明无需调查的理由。

### V11-03：执行授权分层（P0）

**修改位置建议**：重写“权限设计”章节，统一任务书中的权限字段。

明确三层概念：

1. **任务书建议权限**：为了完成任务，建议执行 Agent 可以做的操作；只是方案建议。
2. **用户已批准的执行权限**：用户在任务书确认后，另外明确授权的具体操作。
3. **禁止操作**：明确不得执行的操作，除非用户通过新的明确授权变更边界。

关键规则：

- 任务书中出现“允许执行”不代表用户已经授权。
- 用户确认任务书，不自动等于授权所有执行动作。
- 文件修改、删除、覆盖、批量迁移、修改规范/模板、代码重构、Git 提交/推送、外部发布等高影响操作，应逐项明确授权范围。
- 未获得授权时，Agent 可以继续做已授权的只读分析，但不得实施未授权的变更。
- 如果用户只授权某些文件或操作，不得扩大到其他文件或操作。

**验收标准**：

- 任务书明确区分建议权限与已批准权限。
- 对未授权的高影响操作，输出中明确标记“需要用户确认”。
- 不会把任务书定稿描述为执行授权。

### V11-04：强化单问题逐轮澄清（P1）

**修改位置建议**：“少而关键的提问”和“交互澄清”章节。

行为规则：

- 每轮只提出一个最关键的问题。
- 可以在一个问题中提供互斥选项，但不得把多个独立决策捆绑成一个问题。
- 将当前阻断问题与后续执行前置条件分开管理。
- 完整任务书可以列出所有待确认项，但交互时不要求用户一次性回答全部事项。
- 用户回答后，更新需求状态，再决定下一个问题；信息足够时停止追问。

**验收标准**：

- 用户提出多个未决事项时，Agent 优先选择影响任务方向最大的一个问题。
- 不在同一轮同时要求用户确认目标、型号、输出格式和执行权限，除非这些信息确实构成一个不可分割的决策。
- 不重复询问已经明确的信息。

### V11-05：完善成熟度判定（P1）

**修改位置建议**：“任务成熟度模型”。

增加判定约束：

- 任务方向或目标存在阻断性歧义时，成熟度不得判为 M3 或 M4。
- 方案步骤、交付物、权限和验收尚未明确时，不得判为 M3。
- M4 必须同时满足质量检查通过和用户明确确认定稿。
- M4 仍不代表用户已授权执行。
- 任务书章节齐全不等于任务成熟度高。

**验收标准**：

- 对目标路线仍需用户选择的任务，最高暂定为 M2。
- 任务方案完整但用户尚未确认定稿，不得标记 M4。
- 输出成熟度时，简要说明未达到下一等级的原因。

### V11-06：强化验收标准结构（P1）

**修改位置建议**：“验收标准规范”及任务书模板。

每项重要验收标准尽量包含：

1. 检查对象；
2. 通过条件；
3. 验证方法；
4. 证据或记录；
5. 失败/部分通过时的处理方式。

对于无法自动判断的专业结论，明确标记人工评审及评审责任方。

**验收标准**：

- 避免仅使用“内容完善”“质量良好”“检查通过”等主观描述。
- 关键交付物有可检查的完成条件。
- 无法完成的项目允许以 BLOCKED 或 PARTIAL 记录，不得伪装为 PASS。

### V11-07：增加固定回归测试用例（P1）

**修改位置建议**：新增或扩展 `tests/` 下的测试文档，并在 README 中增加测试记录入口。

固定测试场景：

| 用例 | 场景 | 主要检查点 |
|---|---|---|
| TA-01 | 只有模糊想法 | 先理解并提出关键澄清问题 |
| TA-02 | 明确要求验证 Skill | 识别流程验证，不开展真实任务 |
| TA-03 | 已有部分成果 | 调查现状、复用成果、识别重复建设 |
| TA-04 | 只要求方案设计 | 输出方案，不默认安排实施 |
| TA-05 | 涉及高影响操作 | 严格区分建议权限和实际授权 |
| TA-06 | 用户中途改变需求 | 同步更新范围、交付物和验收标准 |
| TA-07 | 输入资料不可访问 | 明确未知，不声称已读取 |
| TA-08 | 需求基本完整 | 减少不必要追问，进入方案或任务书阶段 |

**验收标准**：

- 每个用例有输入、预期行为和判定结果。
- 每次 Skill 版本升级至少执行核心用例 TA-01、TA-02、TA-03、TA-05。
- 记录 PASS / PARTIAL / FAIL / BLOCKED 及失败证据。
- 不把一次人工模拟测试描述为自动化回归测试。

### V11-08：优化待确认项呈现（P2）

**修改位置建议**：任务书初稿输出规范。

将待确认事项分为：

- **当前阻断问题**：不回答就无法确定任务方向或继续形成可靠方案。
- **执行前置条件**：当前可以先完成任务书，但实际执行前必须确认。
- **非阻断优化项**：可以采用明确标注的默认值，后续再调整。

**验收标准**：

- 用户能一眼识别当前最需要回答的问题。
- 不把所有待确认事项都标记为阻断项。
- 任务书保留完整待确认记录，避免信息丢失。

## 4. 建议实施顺序

建议按以下顺序实施：

1. 先修改 `SKILL.md`：V11-01、V11-02、V11-03。
2. 再修改 `SKILL.md`：V11-04、V11-05、V11-06、V11-08。
3. 补充固定回归测试用例和测试记录模板。
4. 更新 `README.md` 的能力说明、流程说明和测试入口。
5. 使用 TA-01、TA-02、TA-03、TA-05 进行首轮回归。
6. 审查差异，确认没有削弱 V1.0 已有的需求分析、用户审查和授权边界。
7. 用户确认后再将 V1.1 标记为正式版本。

## 5. 本次不建议做的事情

- 不重写整个 Skill。
- 不引入复杂的多 Agent 协作机制。
- 不增加强制问卷或大量固定表单。
- 不让 Task Architect 直接执行任务书。
- 不因单次测试结果就宣称所有任务类型均已验证。
- 不删除 V1.0 测试记录或历史版本信息。

## 6. V1.1 完成定义

V1.1 只有满足以下条件，才建议标记为完成：

- [ ] 任务意图三态预判规则已加入。
- [ ] 任务现状调查已加入标准流程。
- [ ] 事实核验与推断信息明确区分。
- [ ] 任务书建议权限与用户实际授权明确分离。
- [ ] 单问题逐轮澄清规则得到强化。
- [ ] 成熟度模型具有阻断项约束。
- [ ] 关键验收标准具备可检查条件和证据。
- [ ] 固定回归测试用例已建立。
- [ ] README 与目录结构说明同步更新。
- [ ] 核心回归测试完成并记录结果。
- [ ] 用户审查并确认 V1.1 定稿。
